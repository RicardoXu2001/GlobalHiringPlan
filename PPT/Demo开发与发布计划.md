# 《牛马公司：全球招聘计划》Demo 开发到发布执行计划 v1.1

制定日期：2026-10-11；执行更新：2026-10-13。依据：《游戏策划案》v0.8。用途：团队认领任务、周交付、验收与 Steam Demo 发布。

**当前执行方式：**当前只有发起人一人。先搭 Godot 可试玩底座并准备可认领工作包，当前任务以 [本周任务与接手清单](../本周任务与接手清单.md) 为准。已建立招聘工程和机制回归；经营、贷款、方针、独立导出包仍待开展。下列十一周排期仅供扩队参考，在成员与工时落实后重新试排；12月窗口尚未确认。当前网页报告与介绍PPT保留旧团队排期，阅读时以本次更新和接手清单为准。


## 1. 目标与排期前提

**交付目标：**一份可以从 Steam 下载并独立完成一局的 Windows Demo，包含招聘扩张、经营取舍、阶段方针、危机、完整胜负、存档和重开。标准速度单局目标 20–25 分钟；真实时长由试玩验证。

**建议发布窗口：2026-12-22 至 12-24。**12-25 至 12-31 留作审核修正或发布缓冲，不将最后一天作为默认首发日。未通过验收时顺延公开日期。

从 10-12 起安排 11 个工作周，另留年底缓冲。该试排以两位程序接近全职、策划和美术稳定交付、QA 持续参与为前提；目前成员技能、实际工时、Steamworks 开户情况尚未确认。已有浏览器原型是规则与美术参考，Godot 招聘工程已起步，新经营系统待制作。已检查的 Godot 4.5.1 标准版可运行；立项时固定版本，并先准备对应导出模板。

第一阶段安排能力与工时盘点；若关键负责人或实际投入不足，按第 8 节调整范围／日期，不能仅凭 6–7 人认定年底一定可完成。

## 5. 从本地版本到 Steam：部署与发布方案

### 5.1 账户、应用与页面

制作人先确认开户、身份／收款／税务资料、权限和主游戏应用；费用与时间按实际账户状态核对。Steam Direct 的 30 天等待与 Coming Soon 至少两周是基础游戏发行说明中的要求，不直接照搬为 Demo 发布倒计时；本项目在第一周处理开户，避免成为末期阻断。[Steam Direct](https://partner.steamgames.com/steamdirect)

Demo 使用与主游戏关联的独立 App ID，有自己的配置、内容仓库和发布清单。主游戏尚未发售时，发布 Demo 前需让主游戏商店处于 Coming Soon。建议首轮让 Demo 挂在主游戏页面，独立 Demo 商店页作为可选项；若选独立页，再按对应清单准备额外素材。[Steam Demo 配置与发布](https://partner.steamgames.com/doc/store/application/demos)

团队材料中的浏览器截图用于内部沟通。公开商店、预告和审核版本的截图重新取自实际 Godot Demo；语言、平台和功能标签仅标已实现且实测的支持范围。股市预览清晰标为正式版内容，不能宣传成 Demo 可交易。

### 5.2 第一次技术上传：W6 前后准备，W8 实测

1. **本地导出：**主程导出 Windows x64 发布版本，用对应导出模板。检查启动文件、资源、图标、游戏版本号、日志和存档路径；导出目录与编辑器工程分开。
2. **干净环境验证：**QA 在未安装 Godot 的另一台 Windows 机器测试启动、新局、完整胜负、继续存档、重开与退出。不能只验证开发电脑。
3. **Demo 配置：**主程与制作人核对 Demo App ID、主游戏关联、Windows 内容仓库、包访问和启动选项；不使用主游戏或示例应用的 ID 误上传。
4. **上传：**使用 Steamworks 的 SteamPipe 工具上传发布文件，并记录构建说明、代码版本、游戏版本、上传时间和 BuildID。账号、口令与凭据不进入项目仓库或交付包。
5. **测试分支：**把候选构建放到受控测试分支，QA 通过 Steam 实际下载安装；测试账户的访问授权单独落实。
6. **复验更新：**用 Steam 从上一测试构建升级，检查存档兼容、启动路径、文件完整性和仍能完成一局。

SteamPipe 上传会生成 BuildID；上传与将构建设置为分支可下载状态是不同步骤。公开默认分支由后台设置；不把“上传成功”当作“已发布”。[SteamPipe 上传说明](https://partner.steamgames.com/doc/sdk/uploading)

本项目单人离线 Demo 由 Steam 分发 Windows 文件，不需要为游戏另外部署常驻服务器。反馈先用简单表单或主游戏社区；不为一次 Demo 增加账号、云后端和联网模拟。

### 5.3 发布候选、审核与公开

- **RC1 前：**QA 完成第 6 节清单；制作人核对商店和真实内容；主程保存发布包、版本和测试结果。
- **审核：**完成 Demo 后台发布清单，提交页面／素材及接近最终的构建；制作人跟进意见，主程与美术修订，QA 复验改动。
- **上线决定：**审核通过后仍需团队 G5 验收。制作人决定发布，主程确认所选公开构建，QA 在线配合检查。
- **公开：**完成 Demo 发布操作，并重新发布主游戏商店页以显示下载按钮；用普通账户核查页面、下载、启动和版本。仅通过审核不等于已公开。[Steam Demo 发布步骤](https://partner.steamgames.com/doc/store/application/demos)

愿望单通知和活动曝光另行安排，不作为上线前置条件。是否参加节庆及资格在活动报名时单独核实，本计划不绑定未经确认的活动日期。

## 6. 验收清单：哪些不通过就不能公开

| 门槛 | 必须有的证据 | 负责人 |
| --- | --- | --- |
| 游戏完整 | 启动→起点→招聘／经营／方针→危机→胜利或失败→重开；真实构建录像／记录 | QA；主程修复 |
| 策略成立 | 至少两种不同方针组合可完成一局；合理贷款救援与过度扩张失败可解释 | 策划 + QA；两位程序协作 |
| 账目正确 | 应收与现金分离、借款不算收入、费用与到期提示一致；暂停／快进不重复或漏结算 | 经济程序 + QA |
| 存档可靠 | 重启继续、贷款和事件恢复、升级兼容；不重抽候选、不刷点或刷新救援窗口 | 主程 + QA |
| 界面与引导 | 两种目标分辨率文字可读、鼠标键盘可操作、窗口可关闭；首次玩家理解费用与失败原因 | 美术／UI 程序 + QA |
| 预览诚实 | 资本市场只读，禁用操作无经济副作用；提示与商店说明一致 | UI 程序 + QA + 制作人 |
| 发布可用 | 干净机器和 Steam 实际安装／更新通过；内容仓库、启动配置、权限和公开版本正确 | 主程 + QA |
| 内容可发布 | 素材授权、名称／文案／截图、平台与语言支持核对；审核清单完成 | 制作人 + 美术 + QA |

外部试玩建议至少两轮，每轮约 5–8 位未参与制作的人，尽量包含首次接触者；这是样本计划而非已完成结果。记录是否能独立开始、理解招聘点与现金、解释一次现金缺口、选择方针所需时间、局内暂停时长和下一局想改变什么。时长区分模拟时长、操作／阅读／暂停与快进，不能只拿自动脚本的胜率和速度判断好玩。

缺陷分级：P0 为无法启动、无法正常存档／继续、严重数据损坏、胜负无法达成；P1 为关键规则、界面或结算错误。已知 P0/P1 必须解决并回归；一般视觉或文案问题登记后由制作人评估。平台审核通过不替代团队玩法验收。

## 7. 上线当天与发布后维护

### 上线当天

- 制作人：确认审核和 G5 结论，批准公开；发布准确公告，说明 Demo 内容与反馈方式。
- 主程：确认 BuildID 与公开包一致，保留前一稳定版本和构建记录；核对启动路径与更新状态。
- QA：通过普通账户验证下载按钮、安装、新局、存档继续、退出和游戏版本；检查反馈入口可用。
- 策划／美术：协助定位首局困惑和关键素材／文本问题，不在上线当天临时增加功能。

### 首周

发布后 24 小时优先观察下载／启动／存档阻断；随后 72 小时整理失败原因、教程困惑和崩溃线索。第一周完成缺陷分类和优先级，按严重程度安排补丁，修复包先进入测试分支，再升级公开构建。

回退方案：保留可重新选用的已验证构建、对应配置和存档版本；QA 先检查旧构建能否读取当前存档。涉及新存档格式时，不能只回退游戏文件，应使用兼容读取或先备份，并说明影响。Steam 分支切换是部署操作，回退是否安全取决于实际数据兼容。

首周复盘交付：公开构建版本、下载／运行反馈、问题与修复记录、两种路线的试玩结果、时长分布，以及正式版范围建议。未配置遥测时使用访谈和自愿提交的日志／反馈，不虚构完成率或愿望单增长。

| 11-08 没有可赢可输的完整经营局 | 暂停扩充事件和表现，优先让核心成立；重新评估年底窗口 |
| 11-22 仍在补基础系统 | 缩减额外插画、复杂动画和第 9–12 个事件；预览用固定说明；已确定核心缺口继续修复 |
| 12-04 功能冻结时核心不稳 | 不加入更多公司、完整金融或新输入平台；缩小版本需更新策划与商店，并重新验收 |
| 没有 UI 程序，主程负担过重 | 先复用统一面板和已有图标，减少动效；美术／策划提前给清晰状态，主程保持每周可运行版本 |
| 审核不通过或等待超出缓冲 | 优先修改反馈项并复验，顺延发布日期；不把未经审核的版本宣布为 Steam 已上线 |
| 存档与更新出现严重问题 | 停止公开升级，修复或采用已验证的兼容回退路径，优先保护已有进度 |

削减建议先落在表现和额外内容。招聘—经营—构筑—危机—完整胜负是本次体验主线；若必须改变这些核心范围，制作人应明确修订版本计划，不能在商店仍保留旧承诺。

## 9. 第一周可以直接认领的任务

- [ ] 制作人：记录成员职责、每周工时和可投入周期，确认 Demo 范围与发布账户状态。
- [ ] 策划：交地区／连接表、升级节点表、方针与事件清单、现金／工资／贷款口径。
- [ ] 主程：固定 Godot 版本与导出模板，建立地图、输入、时间与招聘样例，交可启动的 Windows 包。
- [ ] 经济程序：交可复算账目样例与结算接口，和主程约定统一时间与状态。
- [ ] 美术：交地图主界面、财务和方针线框、风险状态与资源规格。
- [ ] QA：建立启动／完整对局／存档／账目检查表，验证首份 Windows 包。
- [ ] UI 程序（如有）：接入首屏 HUD 与地区面板，和两位程序明确读取与操作接口。

每周任务记录至少包含：负责人、前置任务、交付文件／构建、验收条件、预计工时、状态与风险。周中整合、周末试玩；未完成项先说明影响，再决定下一周范围。
